# Unsafe Rust でできること {#what-unsafe-rust-can-do}

Unsafe Rust で違うのは、次のことができるという点だけです。

* 生ポインタを参照外しする
* `unsafe` な関数を呼び出す（C の関数、コンパイラの組み込み関数（intrinsics）、生のアロケータを含みます）
* `unsafe` なトレイトを実装する
* 可変な static にアクセスする、または変更する
* `union` のフィールドにアクセスする

これだけです。これらの操作が Unsafe の側に追いやられているのは、どれか 1 つでも誤って使うと、あの恐るべき未定義動作を引き起こすからです。未定義動作を引き起こすと、コンパイラはあなたのプログラムに対して、どんなひどいことでも行う完全な権利を得ます。未定義動作は絶対に引き起こす*べきではありません*。

C と違い、Rust では未定義動作の範囲はかなり限られています。言語の中核が気にかけるのは、次のことを防ぐことだけです。

* ダングリングしている、または整列（アライン）されていないポインタを参照外しする（`*` 演算子を使う）こと（後述）
* [ポインタのエイリアシング規則][pointer aliasing rules]を破ること
* 誤った呼び出し ABI で関数を呼び出すこと、または誤った巻き戻し ABI の関数から巻き戻すこと
* [データ競合][race]を引き起こすこと
* 現在の実行スレッドが対応していない [target features][] でコンパイルされたコードを実行すること
* 不正な値を生み出すこと（単独の場合も、`enum` ・ `struct` ・配列・タプルといった複合型のフィールドとしての場合も含みます）:
  * 0 でも 1 でもない `bool`
  * 不正な判別子（discriminant）を持つ `enum`
  * ヌルの `fn` ポインタ
  * [0x0, 0xD7FF] と [0xE000, 0x10FFFF] の範囲から外れた `char`
  * `!`（この型ではすべての値が不正です）
  * [未初期化メモリ][uninitialized memory]から読み出した整数（`i*`/`u*`）、浮動小数点数の値（`f*`）、生ポインタ、または `str` の中の未初期化メモリ
  * ダングリングしている、整列されていない、または不正な値を指している参照や `Box`
  * 不正なメタデータを持つワイド参照、`Box`、生ポインタ:
    * `dyn Trait` のメタデータは、ポインタや参照が指している実際の動的なトレイトに合致する、`Trait` 用の vtable へのポインタでなければ不正です
    * スライスのメタデータは、長さが妥当な `usize` でなければ不正です（つまり、未初期化メモリから読み出したものであってはなりません）
  * 独自の不正な値を持つ型で、値がその不正な値のいずれかであるもの。たとえば、ヌルである [`NonNull`] です。（独自の不正な値を求めるのは不安定な機能ですが、`NonNull` のように、安定版の libstd の型のなかにはこれを利用しているものがあります。）

「未定義動作」のより詳しい説明は、[The Reference][behavior-considered-undefined] を参照してください。

値を「生み出す」ことは、値を代入するとき、関数やプリミティブな操作に渡すとき、関数やプリミティブな操作から返すときに、いつでも起こります。

参照やポインタが「ダングリングしている」とは、それがヌルであるか、指しているバイトのすべてが同じ 1 つの割り当て（アロケーション）に属しているわけではないことを言います（したがって特に、それらのバイトはすべて、*何らかの*割り当てに属していなければなりません）。指しているバイトの範囲は、ポインタの値と、指す先の型のサイズで決まります。その結果、範囲が空であれば、「ダングリングしている」は「ヌルである」と同じ意味になります。スライスと文字列はその範囲全体を指していることに注意してください。そのため、長さのメタデータが大きすぎる値に決してならないことが重要です（特に、割り当ては `isize::MAX` バイトより大きくなれないので、スライスと文字列もそれより大きくなれません）。何らかの理由でこれがあまりに面倒であれば、生ポインタを使うことを検討してください。

これだけです。Rust に組み込まれた未定義動作の原因は、これですべてです。もちろん、unsafe な関数やトレイトは、未定義動作を避けるためにプログラムが保たなければならない制約を、ほかにも自由に宣言できます。たとえばアロケータの API は、割り当てられていないメモリを解放することは未定義動作である、と宣言しています。

ただし、こうした制約に違反しても、たいていは巡り巡って、上に挙げた問題のどれかにつながるだけです。追加の制約のなかには、コードをどう最適化できるかについて特別な仮定を置く、コンパイラの組み込み関数に由来するものもあります。たとえば、Vec と Box は、ポインタが常に非ヌルであることを求める組み込み関数を利用しています。

そのほかの怪しげな操作については、Rust はずいぶん寛容です。Rust は、次のことを「安全」と見なします。

* デッドロックする
* [競合状態][race]になる
* メモリをリークする
* 整数をオーバーフローさせる（`+` などの組み込みの演算子で）
* プログラムを異常終了（abort）させる
* 本番のデータベースを削除する

さらに詳しい情報は、[The Reference][behavior-not-considered-unsafe] を参照してください。

とはいえ、こうしたことを実際にやってのけるプログラムは、*おそらく*正しくありません。Rust は、これらがめったに起きないようにする道具をたくさん用意しています。しかし、これらの問題を根本から一律に防ぐのは現実的でないと考えられています。
