# アトミック {#atomics}

Rust は、アトミック（atomics）のメモリモデルを、かなりあからさまに C++20 からそのまま受け継いでいます。これは、このモデルが特に優れているからでも、理解しやすいからでもありません。実際、このモデルはかなり複雑で、[いくつかの欠陥][C11-busted]があることが知られています。むしろこれは、アトミックのモデル化は*誰もが*かなり苦手だという事実に対する、現実的な譲歩です。少なくとも、C/C++ のメモリモデルをめぐる既存のツールや研究の恩恵を受けることはできます。（このモデルが「C/C++11」あるいは単に「C11」と呼ばれているのをよく見かけるでしょう。C は C++ のメモリモデルをそのまま写しているだけです。C++11 はこのモデルの最初の版ですが、その後いくつかのバグ修正を受けています。）

このモデルを本書で完全に説明しようとするのは、かなり絶望的です。このモデルは、気が変になりそうな因果関係のグラフによって定義されており、実用的な形できちんと理解するには本 1 冊が必要です。細かいところまですべて知りたいなら、[C++ の仕様][C++-model]を調べてください。それでも、基本的なことと、Rust の開発者が直面する問題のいくつかは取り上げてみます。

C++ のメモリモデルは、根本的には、私たちが望む意味論と、コンパイラが望む最適化と、ハードウェアが望む一貫性のない混沌との間の溝を埋めようとするものです。*私たち*としては、ただプログラムを書いて、言ったとおりのことを正確に、ただし、ほら、速くやってほしいのです。そうなったら素晴らしいと思いませんか。

## コンパイラによる並べ替え {#compiler-reordering}

コンパイラは根本的に、データの依存関係を減らし、死んだコードを取り除くために、あらゆる種類の複雑な変換を行えるようにしたいと考えています。特に、出来事の実際の順序を大きく変えたり、出来事がまったく起こらないようにしたりすることがあります。たとえば次のように書いたとします。

<!-- ignore: simplified code -->
```rust,ignore
x = 1;
y = 3;
x = 2;
```

コンパイラは、プログラムが次のようにするのが最善だと結論づけるかもしれません。

<!-- ignore: simplified code -->
```rust,ignore
x = 2;
y = 3;
```

これでは、出来事の順序が逆になり、出来事が 1 つ完全に取り除かれています。シングルスレッドの観点からは、これはまったく観測できません。すべての文が実行された後は、まったく同じ状態になっているからです。しかしプログラムがマルチスレッドであれば、`y` に代入される前に `x` に実際に 1 が代入されていることを当てにしていたかもしれません。私たちは、コンパイラがこの種の最適化を行えるようにしておきたいと考えています。性能を大きく改善できるからです。その一方で、プログラムが*言ったとおりのことをする*ことも当てにできるようにしたいのです。

## ハードウェアによる並べ替え {#hardware-reordering}

その一方で、たとえコンパイラが私たちの望みを完全に理解し、その意向を尊重してくれたとしても、今度はハードウェアが私たちを困らせるかもしれません。CPU がもたらす面倒は、メモリ階層という形でやって来ます。確かにハードウェアのどこかには大域的な共有メモリ空間がありますが、それぞれの CPU コアから見ると、それは*とても遠く*、*とても遅い*ものです。それぞれの CPU は、できれば手元にあるデータのキャッシュで作業をし、そのメモリが実際にキャッシュに無いときにだけ、共有メモリとやり取りするという苦労をしたいのです。

結局のところ、それこそがキャッシュの意義ですよね。キャッシュから読むたびに、変わっていないことを念のため確かめに共有メモリまで戻らなければならないとしたら、何の意味があるでしょうか。その結果、ハードウェアは、*ある*スレッドである順序で起きた出来事が、*別の*スレッドでも同じ順序で起きることを保証しません。これを保証するには、CPU に対して、もう少し賢さを抑えるよう伝える特別な命令を出さなければなりません。

たとえば、コンパイラを説得して次のロジックを出力させたとしましょう。

```text
initial state: x = 0, y = 1

THREAD 1        THREAD 2
y = 3;          if x == 1 {
x = 1;              y *= 2;
                }
```

理想的には、このプログラムの最終状態としてありうるのは 2 つです。

* `y = 3`:（スレッド 1 が完了する前にスレッド 2 が検査を行った）
* `y = 6`:（スレッド 1 が完了した後にスレッド 2 が検査を行った）

しかし、ハードウェアが可能にしてしまう 3 つ目の状態があります。

* `y = 2`:（スレッド 2 は `x = 1` を見たが `y = 3` は見ておらず、その後 `y = 3` を上書きした）

CPU の種類によって提供される保証が異なることは、注目に値します。ハードウェアは一般に、強い順序付け（strongly-ordered）のものと弱い順序付け（weakly-ordered）のものという 2 つの種類に分けられます。特に、x86/64 は強い順序付けの保証を提供し、ARM は弱い順序付けの保証を提供します。このことは、並行プログラミングに 2 つの影響をもたらします。

* 強い順序付けのハードウェアでより強い保証を求めても、コストは小さいか、まったくかからないことさえあります。そうしたハードウェアは、すでに無条件で強い保証を提供しているからです。より弱い保証にして性能が向上するのは、弱い順序付けのハードウェアだけかもしれません。

* 強い順序付けのハードウェアでは、弱すぎる保証を求めても、プログラムが厳密には正しくないにもかかわらず、*たまたま*動いてしまう可能性が高くなります。可能であれば、並行アルゴリズムは弱い順序付けのハードウェアでテストすべきです。

## データアクセス {#data-accesses}

C++ のメモリモデルは、プログラムの*因果関係*（causality）について語れるようにすることで、この溝を埋めようとします。一般にこれは、プログラムの各部分とそれを実行しているスレッドとの間に、*先行発生*（happens before）の関係を確立することで行われます。これにより、厳密な先行発生の関係が確立されていないところでは、ハードウェアとコンパイラにプログラムをより積極的に最適化する余地が与えられ、確立されているところでは、より慎重になることが強制されます。こうした関係を伝える手段が、*データアクセス*（data access）と*アトミックアクセス*（atomic access）です。

データアクセスは、プログラミングの世界の基本中の基本です。データアクセスは根本的に同期されておらず、コンパイラはこれを積極的に最適化して構いません。特に、プログラムがシングルスレッドであるという仮定のもとで、コンパイラはデータアクセスを自由に並べ替えられます。ハードウェアも、データアクセスで行われた変更を、好きなだけ怠惰に、一貫性のない形でほかのスレッドへ伝播させて構いません。そして最も重大なことに、データ競合はデータアクセスによって起こります。データアクセスはハードウェアとコンパイラにはとても優しいのですが、これまで見てきたように、同期の取れたコードを書こうとするには*ひどい*意味論しか提供してくれません。いや、それでは言い方が弱すぎます。

**データアクセスだけを使って正しく同期の取れたコードを書くことは、文字どおり不可能です。**

アトミックアクセスは、プログラムがマルチスレッドであることをハードウェアとコンパイラに伝える手段です。それぞれのアトミックアクセスには、ほかのアクセスとの間にどのような関係を確立するかを指定する*順序付け*（ordering）を付けられます。実際には、これは、コンパイラとハードウェアに対して、*してはならない*ことを伝えることに帰着します。コンパイラにとっては、これは主に命令の並べ替えに関わります。ハードウェアにとっては、主に書き込みがほかのスレッドへどのように伝播するかに関わります。Rust が公開している順序付けは次のとおりです。

* Sequentially Consistent（SeqCst）
* Release
* Acquire
* Relaxed

（注: C++ の *consume* 順序付けは、あえて公開していません）

## Sequentially Consistent {#sequentially-consistent}

Sequentially Consistent（逐次一貫性）は、すべての中で最も強力で、ほかのすべての順序付けの制約を含みます。直観的には、逐次一貫な操作は並べ替えることができません。あるスレッドで SeqCst アクセスの前後に起こるすべてのアクセスは、その前後にとどまります。データ競合が無く、逐次一貫なアトミックとデータアクセスだけを使うプログラムには、すべてのスレッドが合意する、プログラムの命令の単一の大域的な実行が存在するという、とても良い性質があります。この実行は、推論するうえでも特に都合の良いものです。各スレッドの個々の実行を交互に織り交ぜたものにすぎないからです。より弱いアトミックの順序付けを使い始めると、これは成り立たなくなります。

逐次一貫性が開発者にとって比較的扱いやすいことには、代償が伴います。強い順序付けのプラットフォームでも、逐次一貫性にはメモリフェンス（memory fence）の出力が伴うのです。

実際には、プログラムの正しさのために逐次一貫性が必要になることはめったにありません。しかし、ほかのメモリ順序に自信が無いのであれば、逐次一貫性は間違いなく正しい選択です。プログラムが必要以上に少し遅く動くほうが、誤って動くよりも確実にましです。また、後からアトミック操作をより弱い一貫性のものに格下げすることは、機械的にはごく簡単です。`SeqCst` を `Relaxed` に変えるだけで終わりです。もちろん、この変換が*正しい*ことを証明するのは、まったく別の問題です。

## Acquire-Release {#acquire-release}

Acquire と Release は、主に対にして使うことを意図したものです。その名前が用途を示唆しています。ロックの獲得（acquire）と解放（release）、そしてクリティカルセクションが重ならないようにすることに、うってつけなのです。

直観的には、acquire アクセスは、それより後のすべてのアクセスがそれより後にとどまることを保証します。ただし、acquire より前に起こる操作は、それより後に起こるように並べ替えられても構いません。同様に、release アクセスは、それより前のすべてのアクセスがそれより前にとどまることを保証します。ただし、release より後に起こる操作は、それより前に起こるように並べ替えられても構いません。

スレッド A があるメモリ位置を release し、その後でスレッド B が*同じ*メモリ位置を acquire すると、因果関係が確立されます。A の release より前に起きたすべての書き込み（アトミックでない書き込みや relaxed なアトミックの書き込みを含みます）は、B の acquire より後に B から観測されます。しかし、ほかのスレッドとの間には因果関係は確立されません。同様に、A と B が*異なる*メモリ位置にアクセスする場合も、因果関係は確立されません。

したがって、release-acquire の基本的な使い方は単純です。あるメモリ位置を acquire してクリティカルセクションを始め、その位置を release して終えます。たとえば、単純なスピンロックは次のようになるでしょう。

```rust
use std::sync::Arc;
use std::sync::atomic::{AtomicBool, Ordering};
use std::thread;

fn main() {
    let lock = Arc::new(AtomicBool::new(false)); // value answers "am I locked?"

    // ... distribute lock to threads somehow ...

    // Try to acquire the lock by setting it to true
    while lock.compare_exchange(false, true, Ordering::Acquire, Ordering::Relaxed).is_err() { }
    // broke out of the loop, so we successfully acquired the lock!

    // ... scary data accesses ...

    // ok we're done, release the lock
    lock.store(false, Ordering::Release);
}
```

強い順序付けのプラットフォームでは、ほとんどのアクセスが release または acquire の意味論を持っているので、release と acquire は多くの場合まったくコストがかかりません。弱い順序付けのプラットフォームでは、そうはいきません。

## Relaxed {#relaxed}

Relaxed アクセスは、文句なしに最も弱いものです。自由に並べ替えることができ、先行発生の関係を何も提供しません。それでも、relaxed な操作はやはりアトミックです。つまり、データアクセスとはみなされず、それに対して行われる読み出し・変更・書き込み（read-modify-write）の操作はすべてアトミックに行われます。relaxed な操作は、確実に起きてほしいけれども、それ以外の点は特に気にしないものに適しています。たとえば、カウンタをほかのアクセスの同期に使っていないのであれば、複数のスレッドが relaxed な `fetch_add` を使ってカウンタを安全にインクリメントできます。

強い順序付けのプラットフォームでは、操作を relaxed にする利点はめったにありません。そうしたプラットフォームは、通常いずれにせよ release-acquire の意味論を提供するからです。しかし、弱い順序付けのプラットフォームでは、relaxed な操作のほうがコストが小さくなることがあります。
