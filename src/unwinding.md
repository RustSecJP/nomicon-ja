# 巻き戻し {#unwinding}

Rust のエラー処理の仕組みは、*段階的*になっています。

* 何かが無くてもおかしくない場合は、Option を使います。
* 何かがうまくいかず、それを無理なく処理できる場合は、Result を使います。
* 何かがうまくいかず、それを無理なく処理できない場合は、スレッドがパニックします。
* 何か壊滅的なことが起きた場合は、プログラムがアボートします。

ほとんどの状況では、Option と Result が圧倒的に好まれます。特に、API の利用者の判断で、パニックやアボートに格上げできるからです。パニックが起きると、スレッドは通常の実行を止めて、スタックを巻き戻します（unwind）。このとき、すべての関数がただちに戻ったかのように、デストラクタが呼ばれます。

1.0 の時点で、Rust はパニックについて、どっちつかずの態度をとっています。遠い遠い昔、Rust は今よりずっと Erlang に似ていました。Erlang と同じように、Rust には軽量タスクがあり、タスクは維持できない状態に達したときにパニックで自分を終わらせるものとされていました。Java や C++ の例外と違って、パニックはいつでも捕まえられるものではありませんでした。パニックを捕まえられるのはタスクの所有者だけで、その時点でパニックを処理しなければ、*その*タスク自身がパニックすることになっていました。

この話では、巻き戻し（unwinding）が重要でした。タスクのデストラクタが呼ばれなければ、メモリやそのほかのシステムリソースがリークしてしまうからです。タスクは通常の実行の中で死ぬものとされていたので、そうなると Rust は、長時間動き続けるシステムにはとても不向きなものになってしまいます。

今日私たちが知っている Rust ができあがっていくにつれて、抽象化をどんどん減らそうとする流れの中で、このプログラミングのスタイルは廃れていきました。軽量タスクは、重量級の OS スレッドの名のもとに葬られました。それでも、1.0 の時点の安定版の Rust では、パニックを捕まえられるのは親スレッドだけです。つまり、パニックを捕まえるには、OS スレッドをまるごと 1 つ起動する必要があります。残念ながら、これはゼロコスト抽象化という Rust の考え方と相容れません。

スレッドを起動せずにパニックを捕まえられる、[`catch_unwind`] という API があります。それでも、これを使うのは控えめにすることを勧めます。特に、Rust の現在の巻き戻しの実装は、「巻き戻さない」場合に大きく最適化されています。プログラムが巻き戻しをしないのであれば、プログラムが巻き戻しの*準備ができている*ことによる実行時のコストは無いはずです。その結果として、実際に巻き戻すときのコストは、たとえば Java より高くなります。通常の状況で巻き戻しをするようなプログラムを作らないでください。理想的には、パニックするのは、プログラミングの誤りか、*極端な*問題のときだけにすべきです。

Rust の巻き戻しと FFI との関わりについては、[FFI の文書の該当する節](ffi.html#ffi-and-unwinding)に説明があります。

[`catch_unwind`]: https://doc.rust-lang.org/std/panic/fn.catch_unwind.html
