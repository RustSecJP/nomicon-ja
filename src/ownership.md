# 所有権とライフタイム {#ownership-and-lifetimes}

所有権（ownership）は、Rust の目玉となる機能です。これによって Rust は、ガベージコレクションを
避けながら、完全にメモリ安全で、しかも効率的でいられます。所有権の仕組みを詳しく見る前に、
この設計の動機を考えてみましょう。

ここでは、ガベージコレクション（GC）が常に最適な解決策とは限らないこと、そして文脈によっては
メモリを手動で管理するのが望ましいことを、あなたが受け入れているものとします。
もし受け入れられないのであれば、別の言語はいかがでしょうか。

GC をどう思うかはさておき、GC がコードを安全にするうえで*とてつもない*恵みであることは、
かなりはっきりしています。何かが*早すぎる時点で*消えてしまうことを、心配する必要がまったくありません
（もっとも、まだそれを指し続けていたかったのかどうかは、別の問題ですが……）。これは、C と C++ の
プログラムが至るところで向き合わなければならない問題です。GC の無い言語を使ったことのある人なら
誰もが一度はやったことのある、次の単純な間違いを考えてみましょう。

```rust,compile_fail
fn as_str(data: &u32) -> &str {
    // compute the string
    let s = format!("{}", data);

    // OH NO! We returned a reference to something that
    // exists only in this function!
    // Dangling pointer! Use after free! Alas!
    // (this does not compile in Rust)
    &s
}
```

Rust の所有権の仕組みは、まさにこれを解決するために作られました。
Rust は `&s` が生きているスコープを知っているので、それが外へ逃げ出すのを防げます。
とはいえ、これは C コンパイラでさえ捕まえられそうな、単純な場合です。コードが大きくなり、
ポインタがさまざまな関数を通って渡されるようになると、事態は複雑になります。やがて C コンパイラは
力尽き、あなたのコードが不健全だと証明するのに十分なエスケープ解析を行えなくなります。
その結果、あなたのプログラムは正しいという仮定のもとで、受け入れざるをえなくなります。

Rust では、こんなことは決して起こりません。すべてが健全であることをコンパイラに証明するのは、
プログラマーの役目です。

もちろん、所有権をめぐる Rust の話は、参照がその参照先のスコープから逃げ出さないことを
検証するだけ、というよりもずっと複雑です。ポインタが常に有効であると保証することが、
それよりずっと複雑だからです。
たとえば、次のコードでは

```rust,compile_fail
let mut data = vec![1, 2, 3];
// get an internal reference
let x = &data[0];

// OH NO! `push` causes the backing storage of `data` to be reallocated.
// Dangling pointer! Use after free! Alas!
// (this does not compile in Rust)
data.push(4);

println!("{}", x);
```

素朴なスコープ解析では、このバグを防ぐのに不十分です。`data` は実際、必要な間ずっと
生きているからです。しかし、それを指す参照を持っている間に、`data` は*変更されました*。
Rust が、どの参照に対しても、参照先とその所有者を凍結するよう求めるのは、このためです。
