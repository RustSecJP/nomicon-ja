# Safe と Unsafe の関わり方 {#how-safe-and-unsafe-interact}

Safe Rust と Unsafe Rust はどんな関係にあるのでしょうか。両者はどのように関わり合うのでしょうか。

Safe Rust と Unsafe Rust の分離は `unsafe` キーワードで制御されます。このキーワードが、一方からもう一方へのインターフェースの役割を果たします。Safe Rust が安全な言語だと言えるのはこのためです。安全でない部分はすべて、`unsafe` という境界の向こう側だけに閉じ込められています。望むなら、コードベースに `#![forbid(unsafe_code)]` を入れて、Safe Rust しか書いていないことを静的に保証することもできます。

`unsafe` キーワードには 2 つの使い道があります。コンパイラが検査できない契約が存在すると宣言することと、その契約が守られていることをプログラマーが確認したと宣言することです。

`unsafe` を使うと、_関数_ と _トレイト宣言_ に、検査されない契約があることを示せます。関数に付けた `unsafe` は、その関数を使う人が関数のドキュメントを確認し、関数が求める契約を保つ使い方をしていると確かめなければならない、という意味です。トレイト宣言に付けた `unsafe` は、そのトレイトを実装する人がトレイトのドキュメントを確認し、自分の実装がトレイトの求める契約を保っていると確かめなければならない、という意味です。

ブロックに `unsafe` を付けると、その中で行うすべての unsafe な操作について、それぞれの操作の契約を守っていると検証済みであることを宣言できます。たとえば、[`slice::get_unchecked`][get_unchecked] に渡す添字が範囲内である、といったことです。

トレイトの実装に `unsafe` を付けると、その実装がトレイトの契約を守っていることを宣言できます。たとえば、[`Send`] を実装する型が、別のスレッドへ移動しても本当に安全である、といったことです。

標準ライブラリには unsafe な関数がいくつもあります。たとえば次のものです。

* [`slice::get_unchecked`][get_unchecked] は、検査なしで添字アクセスを行います。そのため、メモリ安全性をいくらでも破ることができます。
* [`mem::transmute`][transmute] は、ある値を指定した型の値として解釈し直します。型安全性を好きなように迂回できます（詳しくは[型変換][conversions]を参照してください）。
* サイズの決まった型への生ポインタはどれも [`offset`][ptr_offset] メソッドを持っており、渡したオフセットが[「範囲内」][ptr_offset]でなければ、未定義動作を引き起こします。
* FFI（Foreign Function Interface、他言語関数インターフェース）の関数は、すべて呼び出しが `unsafe` です。相手の言語は、Rust コンパイラが検査できない任意の操作を行えるからです。

Rust 1.29.2 の時点で、標準ライブラリは次の unsafe なトレイトを定義しています（ほかにもありますが、まだ安定化されておらず、なかには永遠に安定化されないものもあるかもしれません）。

* [`Send`] はマーカートレイト（API を持たないトレイト）で、実装する型が別のスレッドへ安全に送れる（移動できる）ことを約束します。
* [`Sync`] はマーカートレイトで、実装する型を、複数のスレッドが共有参照を通じて安全に共有できることを約束します。
* [`GlobalAlloc`] は、プログラム全体のメモリアロケータを差し替えられるようにします。

Rust の標準ライブラリの多くも、内部で Unsafe Rust を使っています。これらの実装はおおむね人の手で厳密に検査されているので、その上に作られた Safe Rust のインターフェースは安全だと考えてかまいません。

こうした分離がすべて必要になる理由は、突き詰めると Safe Rust のただ 1 つの基本的な性質、すなわち*健全性（soundness）の性質*に行き着きます。

**何があっても、Safe Rust の利用者が未定義動作を引き起こすことはできない。**

safe と unsafe をこのように分ける設計にしたことで、Safe Rust と Unsafe Rust の間には非対称な信頼関係が生まれます。Safe Rust は本質的に、自分が触れる Unsafe Rust がすべて正しく書かれていると信頼するしかありません。一方、Unsafe Rust は、よく注意せずに Safe Rust を信頼することはできません。自分が利用者として使っている Safe Rust は信頼できますが、自分の利用者が選んだり渡したりしてくる Safe Rust は信頼できません。

例を挙げます。Rust には [`PartialOrd`] と [`Ord`] というトレイトがあり、「単に」比較できるだけの型と、「全」順序（おおまかに言えば、比較がまともに振る舞うこと）を備えた型とを区別しています。

[`BTreeMap`] は、半順序しか持たない型に対してはあまり意味をなさないので、キーが `Ord` を実装していることを要求します。ところが、`BTreeMap` の実装の中には Unsafe Rust のコードがあります。いい加減な `Ord` の実装（これは Safe に書けます）が未定義動作を引き起こすことは受け入れられません。そのため、BTreeMap の中の Unsafe なコードは、実際には全順序になっていない `Ord` の実装に対しても堅牢であるように書かなければなりません。`Ord` を要求するのは、まさに全順序であってほしいからなのに、です。

Unsafe Rust のコードは、Safe Rust のコードが正しく書かれているとは、とにかく信頼できないのです。とはいえ、全順序を持たない値を与えれば、`BTreeMap` はやはりまったくでたらめな振る舞いをします。ただ、未定義動作だけは決して引き起こしません。

ここで疑問に思うかもしれません。`Ord` は Safe だから `BTreeMap` はそれを信頼できない、というのなら、なぜ Safe なコードを*少しでも*信頼できるのでしょうか。たとえば `BTreeMap` は、整数とスライスが正しく実装されていることに頼っています。これらも safe ですよね。

違いは範囲にあります。`BTreeMap` が整数とスライスに頼るとき、頼っているのはごく特定の 1 つの実装です。これは見積もることのできるリスクで、利益と比べて判断できます。この場合、リスクは事実上ゼロです。整数とスライスが壊れていたら、*誰もが*壊れているからです。しかも、それらを保守しているのは `BTreeMap` を保守しているのと同じ人たちなので、目を配っておくのも簡単です。

同じことは、クレートの境界をまたいでも成り立ちます。クレート `foo` がクレート `bar` に依存しているとします。このとき、クレート `foo` の中の Unsafe Rust は、クレート `bar` の中の Safe Rust を信頼してかまいません。クレート `foo` はクレート `bar` に依存することを自分で選び、そうすることで、クレート `bar` が正しく実装されていると信頼したからです。

これに対して、`BTreeMap` のキーの型はジェネリックです。その `Ord` の実装を信頼するということは、任意の利用者による `Ord` の実装を信頼するということです。こちらはリスクが高くなります。どこかの誰かが間違えて `Ord` の実装を台なしにするでしょうし、「動いているように見えるから」と、全順序を備えているとあからさまに嘘をつくことさえあるでしょう。そうなったときのために、`BTreeMap` は備えておく必要があります。

渡されてきたクロージャが正しく振る舞うと信頼することについても、同じ理屈が当てはまります。

この、ジェネリックなものへの際限のない信頼という問題こそ、`unsafe` なトレイトが解決するために存在する問題です。理屈のうえでは、`BTreeMap` 型はキーに対して、`Ord` ではなく `UnsafeOrd` という新しいトレイトの実装を要求することもできます。それは次のようなものになるでしょう。

```rust
use std::cmp::Ordering;

unsafe trait UnsafeOrd {
    fn cmp(&self, other: &Self) -> Ordering;
}
```

そうすると、型は `unsafe` を使って `UnsafeOrd` を実装することになり、トレイトが期待する契約を自分の実装が保っていると確かめたことを示します。この状況であれば、`BTreeMap` の内部にある Unsafe Rust が、キーの型の `UnsafeOrd` の実装は正しいと信頼しても、筋が通ります。もし正しくなければ、それは unsafe なトレイトを実装した側の落ち度であり、Rust の安全性の保証と矛盾しません。

トレイトに `unsafe` の印を付けるかどうかは、API 設計上の選択です。safe なトレイトのほうが実装しやすいのですが、それに頼る unsafe なコードは、誤った振る舞いから身を守らなければなりません。トレイトを `unsafe` にすると、この責任が実装する側へ移ります。Rust は伝統的に、トレイトを `unsafe` にすることを避けてきました。Unsafe Rust があちこちに広がってしまい、それは望ましくないからです。

`Send` と `Sync` が unsafe とされているのは、スレッド安全性が*基本的な性質*であり、バグのある `Ord` の実装から身を守るのと同じやり方では、unsafe なコードがそこから身を守ることをとうてい望めないからです。同じように、`GlobalAlloc` は、プログラム中のすべてのメモリと、その上に作られる `Box` や `Vec` などの帳簿を付けています。これがおかしなこと（まだ使用中なのに、同じメモリ領域を別の要求に渡してしまうなど）をしたら、それを検出して手を打つ機会はありません。

自分のトレイトを `unsafe` にするかどうかも、同じ種類の検討で決まります。壊れたトレイト実装から身を守ることを `unsafe` なコードに無理なく期待できないのであれば、そのトレイトを `unsafe` にするのは妥当な選択です。

余談ですが、`Send` と `Sync` は `unsafe` なトレイトである一方で、そう導出しても安全だと証明できる場合には、型に対して自動的に実装*も*されます。`Send` は、`Send` を実装する型の値だけで構成されたすべての型に対して、自動的に導出されます。`Sync` は、`Sync` を実装する型の値だけで構成されたすべての型に対して、自動的に導出されます。これにより、この 2 つのトレイトを `unsafe` にしたことで安全でなさが広がってしまうのを、最小限に抑えています。そして、メモリアロケータを*実装する*人（さらに言えば、直接使う人）は、そう多くありません。

これが、Safe Rust と Unsafe Rust の間の釣り合いです。この分離は、Safe Rust をできる限り使いやすくするように設計されていますが、Unsafe Rust を書くときには余分な労力と注意を求めます。この本の残りの部分は、主に、どんな注意を払わなければならないのか、Unsafe Rust がどんな契約を守らなければならないのかについての話です。
