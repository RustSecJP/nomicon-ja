# 境界のないライフタイム {#unbounded-lifetimes}

unsafe なコードは、参照やライフタイムを何もないところから作り出してしまうことがよくあります。そうしたライフタイムは、*境界のない*（unbounded）ものとして生まれてきます。最もよくある原因は、生ポインタを参照外ししたものへの参照を取ることで、これは境界のないライフタイムを持つ参照を生み出します。このようなライフタイムは、文脈が求めるだけ大きくなります。これは実のところ、単に `'static` になるよりも強力です。たとえば `&'static &'a T` は型検査に失敗しますが、境界のないライフタイムは必要に応じて `&'a &'a T` にぴったり形を合わせるからです。とはいえ、ほとんどの目的においては、このような境界のないライフタイムは `'static` とみなしてかまいません。

`'static` である参照はほとんど無いので、これはおそらく誤りです。`transmute` と `transmute_copy` が、ほかの 2 つの主な原因です。境界のないライフタイムには、できるだけ早く境界を付けるように努めるべきです。関数の境界をまたぐ場合は特にそうです。

ある関数について、入力に由来しない出力ライフタイムは、どれも境界がありません。たとえば次のとおりです。

<!-- no_run: This example exhibits undefined behavior. -->
```rust,no_run
fn get_str<'a>(s: *const String) -> &'a str {
    unsafe { &*s }
}

fn main() {
    let soon_dropped = String::from("hello");
    let dangling = get_str(&soon_dropped);
    drop(soon_dropped);
    println!("Invalid str: {}", dangling); // Invalid str: gӚ_`
}
```

境界のないライフタイムを避ける最も簡単な方法は、関数の境界でライフタイムの省略を使うことです。出力ライフタイムが省略されていれば、それは*必ず*入力ライフタイムによって境界付けられます。もちろん、*間違った*ライフタイムで境界付けられることはありえます。しかしその場合は、たいていコンパイルエラーになるだけで、メモリ安全性がたやすく破られることにはなりません。

関数の中では、ライフタイムに境界を付ける作業はもっと間違いやすくなります。ライフタイムに境界を付ける最も安全で簡単な方法は、境界のあるライフタイムを持つ関数からそれを返すことです。しかし、それが受け入れられない場合は、特定のライフタイムを持つ場所に参照を置くこともできます。残念ながら、関数に関わるすべてのライフタイムに名前を付けることはできません。
