# メモリの割り当て {#allocating-memory}

`NonNull` を使うと、Vec の（そして実のところ std のすべてのコレクションの）重要な特徴に支障が出ます。空の Vec を作っても、実際にはまったく割り当てを行わない、という特徴です。これは、大きさがゼロのメモリブロックを割り当てることとは違います。それはグローバルアロケータでは許されていません（未定義動作になります）。では、割り当てができず、かといって `ptr` にヌルポインタを入れることもできないとしたら、`Vec::new` では何をすればよいのでしょうか。そう、何か別のごみを入れておけばよいのです。

これはまったく問題ありません。割り当てが無いことを示す番兵として、すでに `cap == 0` があるからです。ほとんどどのコードでも、これを特別に扱う必要さえありません。たいていは、いずれにせよ `cap > len` や `len > 0` であるかを検査する必要があるからです。ここに入れる値として Rust で推奨されているのは `mem::align_of::<T>()` です。`NonNull` は、そのための便利な手段として `NonNull::dangling()` を提供しています。語るべき実際の割り当ては無いけれども、`null` ではコンパイラがまずいことをしてしまう、という理由で `dangling` を使いたくなる場所はかなりたくさんあります。

そこで、次のようにします。

<!-- ignore: explanation code -->
```rust
use std::mem;

impl<T> Vec<T> {
    pub fn new() -> Self {
        assert!(mem::size_of::<T>() != 0, "We're not ready to handle ZSTs");
        Vec {
            ptr: NonNull::dangling(),
            len: 0,
            cap: 0,
        }
    }
}
# fn main() {}
```

ここに assert を紛れ込ませたのは、ゼロサイズ型（zero-sized type）にはコード全体を通じて特別な扱いが必要になり、その問題をひとまず先送りにしたいからです。この assert が無いと、初期の下書きのいくつかは、とてもまずいことをしてしまいます。

次に、領域が*実際に*欲しくなったときに何をするのかを考える必要があります。そのためには、グローバルな割り当て関数である [`alloc`][alloc]、[`realloc`][realloc]、[`dealloc`][dealloc] を使います。これらは安定版の Rust でも、[`std::alloc`][std_alloc] にあるものを利用できます。これらの関数は、[`std::alloc::Global`][Global] 型が安定化された後、その型のメソッドに取って代わられて非推奨になる見込みです。

メモリ不足（OOM）の状況を扱う手段も必要です。標準ライブラリは [`alloc::handle_alloc_error`][handle_alloc_error] という関数を提供しており、これはプラットフォーム固有の方法でプログラムをアボートします。パニックではなくアボートするのは、巻き戻しが割り当てを引き起こす可能性があるからです。アロケータが「もうメモリが無いんだけど」と言って戻ってきた直後にそれをするのは、良くないことに思えます。

もちろん、これは少しばかげています。ほとんどのプラットフォームでは、実際には普通の形でメモリが尽きることは無いからです。本当にすべてのメモリを使い果たし始めたら、おそらくオペレーティングシステムが別の手段でアプリケーションを強制終了するでしょう。私たちが OOM を引き起こす可能性が最も高いのは、途方もない量のメモリ（たとえば理論上のアドレス空間の半分）を一度に要求した場合です。そのため、パニックしても*おそらく*問題は無く、悪いことは何も起こらないでしょう。それでも、できる限り標準ライブラリと同じようにしたいので、プログラム全体を終了させることにします。

さて、これで伸長の処理を書けます。おおよそ、次のようなロジックにしたいところです。

```text
if cap == 0:
    allocate()
    cap = 1
else:
    reallocate()
    cap *= 2
```

しかし、Rust でサポートされている唯一のアロケータ API はとても低水準なので、かなりの追加作業が必要になります。また、本当に大きな割り当てや空の割り当てで起こりうる、いくつかの特殊な状況にも備えなければなりません。

特に、`ptr::offset` には大いに悩まされることになります。これは LLVM の GEP inbounds 命令の意味論を持っているからです。幸運にもこの命令を扱ったことが無い方のために、GEP の基本的な話をしておくと、こうです。エイリアス解析、エイリアス解析、エイリアス解析。最適化コンパイラにとって、データの依存関係とエイリアスについて推論できることは、きわめて重要なのです。

簡単な例として、次のコード片を考えてみましょう。

<!-- ignore: simplified code -->
```rust
*x *= 7;
*y *= 3;
```

コンパイラが、`x` と `y` がメモリ上の異なる位置を指していると証明できれば、この 2 つの操作は理論上は並列に実行できます（たとえば、別々のレジスタに読み込んで、独立に処理することによって）。しかし、一般にはコンパイラはこれを行えません。x と y がメモリ上の同じ位置を指している場合、操作は同じ値に対して行う必要があり、後から単純に結果を合わせることはできないからです。

GEP inbounds を使うとき、あなたは LLVM に対して、これから行うオフセットが単一の「割り当てられた」実体の範囲内にあると明確に伝えていることになります。最終的な見返りは、2 つのポインタが互いに素な 2 つのオブジェクトを指していると分かっていれば、それらのポインタからのオフセットも*すべて*エイリアスしないと分かっている、と LLVM が仮定できることです（メモリ上のでたらめな場所に行き着くことは無いからです）。LLVM は GEP のオフセットを扱うよう大いに最適化されており、中でも inbounds のオフセットは最良のものなので、できる限りこれを使うことが重要です。

GEP とはそういうものだとして、それがどのように私たちを困らせるのでしょうか。

1 つ目の問題は、私たちは配列を符号なし整数で添字付けするのに、GEP は（そしてその結果として `ptr::offset` も）符号付き整数を取ることです。つまり、配列への一見有効な添字のうち半分は、GEP をオーバーフローさせ、実際には逆の方向へ進んでしまいます。そのため、すべての割り当てを `isize::MAX` 個の要素までに制限しなければなりません。これは実際には、気にする必要があるのはバイトサイズのオブジェクトだけだということを意味します。たとえば `> isize::MAX` 個の `u16` は、本当にシステムのメモリをすべて使い果たしてしまうからです。しかし、誰かが `< isize::MAX` 個のオブジェクトから成る配列をバイト列として再解釈する、といった微妙な特殊ケースを避けるために、std はすべての割り当てを `isize::MAX` バイトまでに制限しています。

Rust が現在サポートしているすべての 64 ビットのターゲットでは、アドレス空間の 64 ビット全部よりも大幅に小さい範囲に人為的に制限されている（現代の x64 プラットフォームは 48 ビットのアドレッシングしか公開していません）ので、先にメモリが尽きるだけだと当てにできます。しかし、32 ビットのターゲット、特にアドレス空間をより多く使うための拡張（PAE x86 や x32）を備えたものでは、`isize::MAX` バイトを超えるメモリの割り当てに成功することが理論的には可能です。

とはいえ、これはチュートリアルなので、ここで特に最適なものを目指すことはしません。プラットフォーム固有の巧妙な `cfg` を使うのではなく、単に無条件で検査します。

気にする必要があるもう 1 つの特殊ケースは、空の割り当てです。気にする必要がある空の割り当てには 2 種類あります。すべての T に対する `cap = 0` と、ゼロサイズ型に対する `cap > 0` です。

これらの場合が厄介なのは、結局のところ、LLVM が「割り当てられた」という言葉で何を意味しているかという話になるからです。LLVM の割り当ての概念は、私たちが普段使っているものよりもかなり抽象的です。LLVM は、さまざまな言語の意味論や独自のアロケータとともに動く必要があるので、割り当てを深く理解することは実際にはできません。その代わり、割り当ての背後にある主な考え方は「ほかのものと重ならない」ということです。つまり、ヒープの割り当て、スタックの割り当て、グローバル変数がでたらめに重なることは無い、ということです。そう、これもエイリアス解析の話です。そのため、Rust は、*一貫して*いる限り、割り当ての概念を技術的には少しいい加減に扱うことができます。

空の割り当ての場合に話を戻すと、ジェネリックなコードの結果として、0 だけオフセットしたい場所が 2、3 あります。そこで問題になるのは、そうすることが一貫しているか、ということです。ゼロサイズ型については、任意の個数の要素分だけ GEP inbounds のオフセットを行うことは確かに一貫している、と結論づけました。どの要素も領域を占めないので、これは実行時には何もしない操作であり、`0x01` に無限個のゼロサイズ型が割り当てられているかのように振る舞っても問題ありません。どのアロケータも、そのアドレスを割り当てることは決してありません。`0x00` を割り当てることは無く、一般に 1 バイトより大きい何らかの最小アラインメントで割り当てるからです。また、一般に、メモリの最初のページ全体は、いずれにせよ割り当てられないよう保護されています（多くのプラットフォームでは 4k まるごとです）。

では、大きさが正の型についてはどうでしょうか。こちらは少し厄介です。原理的には、0 だけオフセットしても LLVM に何の情報も与えない、と主張できます。そのアドレスの前か後に要素があるのですが、どちらなのかは LLVM には分からないからです。しかし私たちは、まずいことが起こるかもしれないと保守的に仮定することを選びました。そのため、この場合には明示的に備えることにします。

*ふう*

さて、ややこしい話はすべて片付いたので、実際にメモリを割り当ててみましょう。

<!-- ignore: simplified code -->
```rust
use std::alloc::{self, Layout};

impl<T> Vec<T> {
    fn grow(&mut self) {
        let (new_cap, new_layout) = if self.cap == 0 {
            (1, Layout::array::<T>(1))
        } else {
            // This can't overflow since self.cap <= isize::MAX.
            let new_cap = 2 * self.cap;
            (new_cap, Layout::array::<T>(new_cap))
        };

        // `Layout::array` checks that the number of bytes allocated is
        // in 1..=isize::MAX and will error otherwise.  An allocation of
        // 0 bytes isn't possible thanks to the above condition.
        let new_layout = new_layout.expect("Allocation too large");

        let new_ptr = if self.cap == 0 {
            unsafe { alloc::alloc(new_layout) }
        } else {
            let old_layout = Layout::array::<T>(self.cap).unwrap();
            let old_ptr = self.ptr.as_ptr() as *mut u8;
            unsafe { alloc::realloc(old_ptr, old_layout, new_layout.size()) }
        };

        // If allocation fails, `new_ptr` will be null, in which case we abort.
        self.ptr = match NonNull::new(new_ptr as *mut T) {
            Some(p) => p,
            None => alloc::handle_alloc_error(new_layout),
        };
        self.cap = new_cap;
    }
}
# fn main() {}
```
