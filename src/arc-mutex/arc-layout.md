# レイアウト {#layout}

まず、私たちの `Arc` の実装のレイアウトを作るところから始めましょう。

`Arc<T>` は、ヒープに割り当てられた `T` 型の値について、スレッド安全な共有所有権（ownership）を提供します。Rust では、共有は不変であることを意味します。それなら、その値へのアクセスを管理するものは何も設計しなくてよいはずですよね。Mutex のような内部可変性の型を使えば、Arc の利用者は共有された可変性を作り出せますが、Arc 自体がこうした問題を気にする必要はありません。

ところが、Arc が変更を気にしなければならない場所が 1 つだけ*あります*。破棄です。Arc の所有者がすべていなくなったとき、その中身を `drop` し、割り当てを解放できなければなりません。そのため、ある所有者が自分が*最後の*所有者かどうかを知る方法が必要です。そのいちばん簡単な方法は、所有者の数を数えること、つまり参照カウント（Reference Counting）です。

残念ながら、この参照カウントは本質的に共有された可変な状態なので、Arc は同期について*考えなければなりません*。これに Mutex を使うことも*できます*が、それは大げさです。代わりにアトミック操作を使います。また、どの所有者もすでに T の割り当てへのポインタを必要としているので、参照カウントも同じ割り当てに置いてしまうのがよいでしょう。

素朴に書くと、次のようになります。

```rust
use std::sync::atomic;

pub struct Arc<T> {
    ptr: *mut ArcInner<T>,
}

pub struct ArcInner<T> {
    rc: atomic::AtomicUsize,
    data: T,
}
```

これはコンパイルできますが、正しくありません。まず、コンパイラが与える変性（variance）が厳しすぎます。たとえば、`Arc<&'a str>` が期待される場所で `Arc<&'static str>` を使えません。さらに重要なのは、ドロップチェッカーに誤った所有権の情報を与えてしまうことです。ドロップチェッカーは、私たちが `T` 型の値を何も所有していないと見なします。これは値の共有所有権を提供する構造体なので、いずれかの時点で、この構造体のあるインスタンスがデータを完全に所有することになります。変性とドロップチェックの詳細は、[所有権とライフタイムの章](../ownership.html)を参照してください。

1 つ目の問題を直すには、`NonNull<T>` を使えます。`NonNull<T>` は生ポインタのラッパーで、次のことを宣言するものです。

* `T` に対して共変である
* ポインタが決して null にならない

2 つ目の問題を直すには、`ArcInner<T>` を含む `PhantomData` マーカーを持たせます。こうすると、私たちが `ArcInner<T>` の値（それ自体が何らかの `T` を含みます）について、ある種の所有権を持っていることがドロップチェッカーに伝わります。

これらの変更を加えると、最終的な構造体になります。

```rust
use std::marker::PhantomData;
use std::ptr::NonNull;
use std::sync::atomic::AtomicUsize;

pub struct Arc<T> {
    ptr: NonNull<ArcInner<T>>,
    phantom: PhantomData<ArcInner<T>>,
}

pub struct ArcInner<T> {
    rc: AtomicUsize,
    data: T,
}
```
