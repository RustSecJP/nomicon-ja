# Safe と Unsafe のご紹介 {#meet-safe-and-unsafe}

![safe と unsafe](img/safeandunsafe.svg)

低レベルな実装の詳細を気にしなくて済むなら、それに越したことはありません。空のタプルがどれだけの領域を占めるかなど、いったい誰が気にするでしょうか。残念ながら、それが問題になることもあり、そのときは気にしなければなりません。開発者が実装の詳細を気にし始める理由として最も多いのは性能です。しかしもっと重要なのは、ハードウェア、オペレーティングシステム、ほかの言語と直接やり取りするとき、こうした詳細が正しさの問題になりうることです。

安全なプログラミング言語で実装の詳細が問題になり始めたとき、プログラマーにはふつう 3 つの選択肢があります。

* コンパイラやランタイムが最適化を行うよう、コードをいじって促す
* 望む実装を得るために、その言語らしくない設計や面倒な設計を採用する
* そうした詳細を扱える言語で、実装を書き直す

最後の選択肢でプログラマーがよく使う言語は *C* です。C のインターフェースしか宣言していないシステムとやり取りするには、多くの場合これが必要になります。

残念ながら、C は使ううえで信じられないほど安全でなく（それにもっともな理由があることもあります）、ほかの言語と相互運用しようとすると、その安全でなさはさらに大きくなります。C ともう一方の言語が、何が起きているのかについて認識を合わせ、互いの邪魔をしないように、注意を払わなければなりません。

では、これが Rust とどう関係するのでしょうか。

まず、C と違って、Rust は安全なプログラミング言語です。

しかし、C と同じく、Rust は安全でないプログラミング言語です。

より正確に言うと、Rust は安全なプログラミング言語と安全でないプログラミング言語の両方を*含んでいます*。

Rust は、*Safe Rust* と *Unsafe Rust* という 2 つのプログラミング言語を組み合わせたものと考えることができます。都合のよいことに、これらの名前はまさに文字どおりの意味です。Safe Rust は安全です。Unsafe Rust は、まあ、そうではありません。実のところ、Unsafe Rust では*本当に*安全でないことができてしまいます。Rust の作者たちがどうかやらないでくれと懇願するようなことですが、私たちはそれでもやります。

Safe Rust こそが、*真の* Rust プログラミング言語です。Safe Rust だけを書いている限り、型安全性やメモリ安全性を心配する必要は決してありません。ダングリングポインタにも、解放後使用（use-after-free）にも、そのほかどんな種類の未定義動作（Undefined Behavior、略して UB）にも、苦しめられることは決してありません。

また、標準ライブラリには最初から十分な道具がそろっているので、純粋で Rust らしい Safe Rust だけで、高性能なアプリケーションやライブラリを書くことができます。

しかし、ほかの言語とやり取りしたいこともあるでしょう。標準ライブラリが公開していない低レベルな抽象を書いていることもあるでしょう。標準ライブラリそのもの（すべて Rust で書かれています）を*書いている*こともあるでしょう。型システムには理解できない何かをする必要があって、とにかく*ビットをいじくり回したい*こともあるでしょう。そんなとき、あなたには Unsafe Rust が必要なのかもしれません。

Unsafe Rust は Safe Rust とまったく同じで、規則も意味論もすべて同じです。ただ、「絶対に安全ではない」こと（次の節で定義します）を、いくつか*余分に*できるだけです。

このように分けることの価値は、C のような安全でない言語を使う利点、つまり実装の詳細に対する低レベルな制御を、まったく別の安全な言語と統合しようとするときに生じる問題のほとんどを抱えることなく得られる点にあります。

それでも、問題はいくつか残ります。なかでも大きいのは、型システムが前提としている性質を把握し、Unsafe Rust と関わるどのコードでもそれらを点検しなければならないことです。それがこの本の目的です。つまり、こうした前提と、それをどう管理するかをお伝えすることです。
